1 in 5 AI Code Suggestions Import a Package That Doesn't Exist. Attackers Have Noticed.

Researchers tested 16 code-generating models across 576,000 samples and found that 19.7% of recommended packages were hallucinated. 43% of those phantom names reappear every single time you ask. Registering them on npm or PyPI costs nothing.

Elena Vasquez Defense & Security Tech June 28, 2026

Two hundred and five thousand, four hundred and seventy-four. That is the number of unique software package names that do not exist in any registry anywhere but were confidently recommended by AI code-generation tools in a comprehensive study published by researchers at the University of Texas at San Antonio and other institutions. Not variations on real package names. Not typos. Entirely fabricated identifiers that the models invented from statistical patterns and recommended as if they were battle-tested production libraries.

The paper, "We Have a Package for You!", tested 16 models across 576,000 code samples in Python and JavaScript. Of the 2.23 million package recommendations generated, 440,445 pointed to packages that do not exist on PyPI or npm. That is a 19.7% hallucination rate across the board, and the rate varies wildly by model: GPT-4 Turbo hallucinated just 3.59% of the time, while CodeLlama 34B fabricated packages in more than a third of its outputs.

Those numbers alone would be a footnote in the long catalog of AI unreliability. What makes them dangerous is a finding buried deeper in the paper's analysis.

Phantom Packages Are Not Random

If an AI model invented a different nonsense package name every time you asked the same question, the security implications would be limited. An attacker would have to register millions of names to catch a handful of victims. But the researchers found precisely the opposite pattern: 43% of hallucinated package names appeared in every single run out of ten consecutive attempts with the same prompt, and 61% reappeared across multiple runs. The hallucinations are not noise. They are signal, stable and reproducible, emerging from the same statistical grooves in the model's training data that produce correct answers the other 80% of the time.

Consider what this means for an attacker. You do not need to monitor every AI conversation in real time. You do not need to compromise a registry or exploit a zero-day. You simply need to ask the same coding questions that millions of developers ask every day, catalog the phantom names that keep appearing, register them on npm or PyPI (both free, both requiring no identity verification), and wait. When a developer asks Copilot how to parse financial data and the model suggests import financial_analytics as fa, the developer runs pip install financial_analytics and gets your payload.

Security researchers have a name for this: slopsquatting, a portmanteau of "AI slop" and "typosquatting" coined by Seth Larson, the Python Software Foundation's Developer-in-Residence, in April 2025. Unlike typosquatting, where attackers register reqeusts and hope someone fat-fingers requests, slopsquatting exploits machine confidence. Nobody misspelled anything. The AI recommended a package that sounded exactly right. The developer trusted the recommendation because the tool that made it also correctly suggested pandas, numpy, and flask on the same line.

The Economics of Free Registration

We ran the numbers on weaponizing the full dataset, and the economics are staggering in their asymmetry.

Publishing a package to npm requires only a free account and a valid email address. PyPI is the same. There is no cost per package, no identity verification, and no limit on how many names a single account can register. An attacker who wanted to claim every one of the 205,474 unique hallucinated package names identified in the study could do so at zero marginal cost. But the 43% repeatability finding means they do not even need to be that ambitious. Roughly 88,000 of those names appear every single time a model encounters a related prompt. Register those 88,000, and you have covered every stable hallucination across 16 models and two programming languages.

The trust differential deserves emphasis. When a human developer types pip install reqeusts and gets an unknown package, there is a moment of friction: I misspelled that. But when GitHub Copilot suggests from jwt_secure_validator import validate_token alongside three legitimate imports, the developer's mental model assigns the unknown package the same credibility as the known ones. The AI said it. It must exist.

One Proof of Concept Already Worked

In 2023, security researcher Bar Lanyado at Vulcan Cyber demonstrated exactly how easily this trust can be exploited. He noticed that multiple AI models consistently hallucinated a package called huggingface-cli, a plausible name because huggingface-cli is the command you use to interact with HuggingFace Hub, but not the actual package name (the real one is huggingface_hub[cli]). Lanyado registered the hallucinated name on PyPI and uploaded an empty package. In three months, it accumulated over 30,000 downloads. The hallucinated name even appeared in an Alibaba research repository's README file, meaning a major tech company's own researchers trusted the AI-generated package name enough to include it in published code.

Thirty thousand installs of an empty package. Imagine if it had contained a credential harvester instead.

Why Registries Cannot Fix This

The structural problem is that package registries are designed to be open. That openness is a feature, not a bug: it is what allows a single developer in Nairobi to publish a utility that gets adopted by teams at Google and JPMorgan. Npm hosts 4.75 million packages. PyPI has 548,000. Both operate on a first-come, first-served naming model with minimal gatekeeping.

Blocking hallucinated names preemptively would require registries to maintain a constantly updating blocklist derived from running inference on every major code-generation model across every plausible prompt, then comparing the output against existing packages. That is not a moderation problem. It is a research problem, and the adversary's cost to generate new hallucinated names is effectively zero because they just need to rephrase the prompt.

Post-hoc detection is equally fraught. A Trend Micro analysis by principal threat researcher Sean Park found that even advanced coding agents like Claude Code CLI and OpenAI's Codex CLI, equipped with MCP-backed package validation, could not eliminate the risk entirely. "Common failure scenarios include context-gap filling and surface-form mimicry," Park wrote, "where agents compose legitimate-sounding packages based on user intent or statistical conventions without robust real-world validation."

The Vibe Coding Multiplier

There is a cultural accelerant that did not exist two years ago. "Vibe coding," the practice of describing what you want in natural language and letting an AI write and run the code, has shifted from an experiment to a production workflow for a growing share of developers. GitHub reported that Copilot had surpassed 1.8 million paying subscribers by late 2024, and the number has only grown since. Cursor, Windsurf, and a dozen other AI-first editors have entered the market.

Feross Aboukhadijeh, CEO of security firm Socket, warned that developers practicing vibe coding may be especially susceptible because the entire workflow is built on not reading the code the AI produces. When the value proposition of your tool is "you don't have to write it yourself," the verification step that catches a fake package name is exactly the step the user is paying to skip.

Meanwhile, the open-source supply chain is already under sustained attack from conventional methods. In May 2026 alone, Socket documented TrapDoor, a coordinated campaign that planted credential-stealing malware in 34 packages across npm, PyPI, and Rust's Crates.io. In June, the Miasma campaign poisoned more than 20 npm packages with secret-stealing payloads. These are traditional supply chain attacks requiring social engineering, account compromise, or typosquatting. Slopsquatting would be cheaper, more scalable, and harder to attribute because the attacker never interacts with the victim at all. The AI does the introduction.

Model Differences Matter (But Not Enough)

Commercial models hallucinate packages at roughly one-quarter the rate of open-source ones: 5.2% versus 21.7%. GPT-4 Turbo's 3.59% hallucination rate is the lowest measured. But "lowest" is relative. At a 3.59% hallucination rate, a developer generating 100 package recommendations through GPT-4 Turbo will encounter roughly 3 to 4 phantom names. Given the volume of AI-assisted code generation happening globally, even that floor produces millions of attack opportunities per year.

The researchers also found that Python code produced fewer hallucinated packages than JavaScript (15.8% versus 21.3%), a result they attribute to npm's vastly larger package universe: 4.75 million packages compared to PyPI's 548,000. More real packages means more plausible-sounding names the model can fabricate by recombining fragments of real ones.

Retrieval Augmented Generation, the technique of grounding model outputs against a live package registry, reduced hallucination rates below 3% for one tested model. But RAG requires real-time connectivity to every relevant registry, adds latency to every suggestion, and is not universally implemented. Most developers using AI code assistance today are getting raw model output with no registry validation layer between the suggestion and the install command.

Limitations

The study tested 16 models available as of mid-2024. Newer models, particularly those with tool-use capabilities that can verify package existence in real time, may perform better, though no comparable study has been published with updated models. The 43% repeatability figure was measured over 10 runs per prompt; longer-term stability across model updates is unknown, as fine-tuning and RLHF iterations may shift which names a model hallucinates. The economic analysis assumes zero identity verification at registries, which is currently accurate for npm and PyPI but could change if either platform implements know-your-publisher policies.

The Strongest Counterargument

The most honest objection is that this attack has not happened yet. Wikipedia's article on slopsquatting, last updated May 2026, explicitly states: "There has not yet been a reported case where slopsquatting has been used as a cyberattack." Every security researcher who has studied the problem calls it a theoretical risk with practical mechanics. That gap between "we showed this works" and "someone actually weaponized it" is real, and in security, the interval between proof of concept and exploitation can stretch from months to years. Some vulnerabilities that researchers panic about never get exploited in the wild because the expected payoff does not justify the effort, or because defenders patch faster than attackers can scale.

The counterargument weakens, though, when you consider the economics. Most supply chain attacks require persistent effort: maintaining fake accounts, social engineering maintainers, targeting specific organizations. Slopsquatting requires registering a batch of free package names and waiting. The effort-to-payoff ratio is among the most favorable in the history of supply chain exploitation. If it has not been weaponized yet, the most likely explanation is not that it is impractical but that the AI coding assistant market has not yet reached the density where the attack becomes worth automating at scale. GitHub Copilot hitting 1.8 million subscribers may not have crossed that threshold. The next doubling probably will.

What You Can Do

If you write code with AI assistance, verify every import and require statement the model generates. Search for the package on PyPI or npm before running pip install or npm install. Check the package's download count, age, and maintainer. A real package with 12 million weekly downloads looks different from a slopsquatted trap with 47 downloads and a creation date three weeks ago.

If you manage a development team, enforce dependency lockfiles (package-lock.json, poetry.lock) and require hash verification for all new dependencies. Tools like Socket, Snyk, and npm audit can flag recently published packages with suspicious characteristics. Consider an internal package allowlist for production deployments.

If you build AI coding tools, implement real-time package validation before suggestions reach the user. The study showed that RAG-based grounding reduced hallucination rates from 19.7% to below 3%. That is not a research challenge anymore. It is an engineering decision, and the cost of not making it is measured in compromised developer machines.

The Bottom Line

Software supply chains have always been trust networks. You install requests because Kenneth Reitz built it, because 40 million developers use it, because its GitHub repository has 14 years of commit history. Slopsquatting breaks that chain by inserting a new kind of trust authority: the AI assistant, which developers are training themselves to believe the way they once believed Stack Overflow's top answers. The difference is that Stack Overflow answers were written by humans who had used the packages they recommended. AI models recommend packages they assembled from statistical proximity to the prompt, and one in five of those recommendations points to something that does not exist. The only question is whether someone fills that void before the registries figure out how to close it.
