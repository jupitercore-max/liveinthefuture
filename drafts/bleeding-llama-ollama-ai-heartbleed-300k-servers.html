Three API Calls, Zero Authentication, 300,000 Servers: Ollama's 'Bleeding Llama' Is AI's Heartbleed Moment

A heap out-of-bounds read in the world's most popular self-hosted AI framework lets attackers silently exfiltrate API keys, user conversations, and cloud credentials. Ollama shipped a patch three months before anyone assigned a CVE number. Its vulnerability class will outlast the fix.

Anya Volkov · Defense & Cybersecurity · July 5, 2026

The Number

Three hundred thousand. That's how many Ollama servers Cyera Research estimates are currently reachable from the open internet, each one running without authentication, each one capable of leaking its entire process memory to anyone who sends three HTTP requests in the right order. No credentials needed. No user interaction. No entry in the logs.

Cyera named it Bleeding Llama (CVE-2026-7482, CVSS 9.1), and the nickname is earned: the attack mechanism, the silence, and the scale are structurally identical to Heartbleed, the 2014 OpenSSL vulnerability that rewrote internet security policy for a generation. But where Heartbleed leaked TLS session fragments, Bleeding Llama leaks what people actually say to their AI.

How It Works

Ollama is the dominant open-source framework for running large language models on local hardware, with over 170,000 GitHub stars and more than 100 million Docker Hub downloads, making it the default inference engine for developers, research labs, and enterprises that want LLM capabilities without sending prompts to a third-party cloud. Its model file format is GGUF (GPT-Generated Unified Format), a binary container that stores model weights, metadata, and tensor dimensions in a single file optimized for fast local inference.

Where this breaks down is in how Ollama processes GGUF files during quantization, the conversion step where model weights are transformed between precision formats (for instance, float-16 to float-32) to optimize for different hardware. When a user uploads a GGUF file via the /api/create endpoint, Ollama reads the tensor dimensions declared in the file header and allocates a buffer accordingly, then reads that many bytes from the file to perform the conversion.

Here's the problem: Ollama's quantization code uses Go's unsafe package to create byte slices from the GGUF file data, and it trusts the declared tensor dimensions without checking whether they exceed the actual file length. An attacker crafts a GGUF file declaring a tensor of, say, 1 × 1 × 1 × 999,999,999 elements, while the file itself contains almost no real data. But Ollama's WriteTo() function in server/quantization.go reads hundreds of kilobytes of adjacent heap memory as though it were part of the tensor, because the byte slice extends past the allocated buffer into whatever the heap allocator placed next.

What happens next is elegant in the worst sense: the float-16 to float-32 conversion is mathematically lossless, so every stolen byte is perfectly preserved in the resulting model weights, not corrupted or truncated but faithfully transcribed into a valid GGUF output file. From there, the attacker calls Ollama's built-in /api/push endpoint to send that model to a registry they control, and the leaked memory arrives as a downloadable model file, neatly packaged, with no trace left on the victim server.

What Bleeds

A running Ollama process holds everything it has touched in memory on the heap: environment variables (AWS keys, OpenAI tokens, database connection strings), system prompts that encode proprietary business logic, active user conversations from concurrent sessions, and whatever else Go's garbage collector hasn't reclaimed. Security Boulevard's analysis emphasizes that detection is nearly impossible without purpose-built endpoint monitoring, because the exploit uses legitimate API endpoints for their intended purpose, and the only anomaly is a model push to an unfamiliar registry, which most Ollama deployments don't monitor at all.

This is the critical difference from a typical buffer overflow: a conventional exploit crashes a process, triggers alerts, or produces error conditions, while Bleeding Llama leaves the server running perfectly. From the operator's perspective, nothing happened, and from the attacker's perspective, they just received a memory dump containing every secret the server had loaded.

Immediately usable data, no reassembly required.

Localhost Illusion

Why are 300,000 Ollama servers exposed to the internet in the first place? A pattern that has played out identically with every developer-friendly database and infrastructure tool of the past decade provides the answer.

Ollama binds to 127.0.0.1:11434 by default, which is safe and local, but the moment a developer wants to run it on a server or share it with a team, every tutorial, every blog post, and every Docker Compose example tells them to set OLLAMA_HOST=0.0.0.0, and there is no authentication mechanism built into Ollama's REST API. There never has been.

Redis went through this exact trajectory, as did MongoDB, as did Elasticsearch. A SentinelOne/Censys study from January 2026 found 175,000 exposed Ollama hosts across 130 countries before CVE-2026-7482 was even disclosed, with fifty-six percent sitting on residential ISP networks. Nearly half had tool-calling capabilities enabled, meaning they could execute code, access APIs, and interact with external systems, and 201 were running prompt templates that explicitly disabled safety guardrails.

What security researchers call the "localhost illusion" is a well-documented failure mode: a tool designed for local use ships without authentication because "you're only running it on your own machine," then adoption outpaces the security roadmap, people expose it because they need to, and by the time an authentication layer ships, the installed base has already calcified around the default auth-free configuration.

CVE Process Gap

Cyera reported the vulnerability to Ollama on February 2, 2026, and Ollama shared a fix on February 25, shipping version 0.17.1 with the patch. Here's the part that should alarm anyone running enterprise AI infrastructure: Ollama didn't flag v0.17.1 as a security release, and the release notes said nothing about CVE-2026-7482. Cyera requested a CVE from MITRE on March 2, but MITRE didn't respond, and it took until April 28 for Echo CNA to assign the CVE number and until May 5 for Cyera to publish the full disclosure.

During those 85 days between fix and CVE assignment, no vulnerability scanner on the market could identify the issue, meaning enterprise security teams that rely on CVE databases for patch prioritization had no signal that v0.17.1 was anything more than a routine update. An open-source AI infrastructure community that does not yet have mature disclosure and notification pipelines left hundreds of thousands of servers in a patching blind spot for nearly three months.

And Bleeding Llama isn't alone in exposing Ollama's security surface. Striga researchers separately disclosed two additional vulnerabilities in Ollama's Windows update mechanism (CVE-2026-42248, CVSS 7.7), combining a missing signature verification with a path traversal to enable persistent code execution on every Windows login, and these were disclosed to Ollama in January 2026, went 90 days without a fix, and were published under responsible disclosure rules while remaining unpatched as of this writing.

Structural Thesis

Bleeding Llama is not a one-off. It is the first visible instance of a vulnerability class that will recur across the AI infrastructure stack: model file formats as memory-read primitives.

GGUF is not the only model format that parsers ingest from potentially untrusted sources. PyTorch's .pt and .pth files are serialized via Python's pickle module, which has been a known arbitrary code execution vector for years. ONNX files carry Protocol Buffer-defined tensor shapes that consuming libraries must validate. Even safetensors, explicitly designed as a safe alternative to pickle-based formats, relies on implementations correctly parsing and bounds-checking header metadata.

Every time a framework reads a model file, it performs a series of memory allocations governed by metadata declared inside that file. If the parser trusts the metadata without bounds checking, the file becomes an attacker-controlled read (or write) primitive. Bleeding Llama exploited this in GGUF's quantization path. Identical bugs can exist in any model-loading code that uses declared dimensions to size memory operations.

Limitations

This analysis relies on Cyera's estimate of 300,000 exposed servers, which is based on internet-wide scanning and may not reflect the full population of vulnerable instances on private networks and VPNs. SentinelOne/Censys measured 175,000 using a different methodology before the CVE disclosure. We have no reliable data on how many servers have upgraded to v0.17.1 since the May 5 disclosure; the actual residual exposure could be significantly higher or lower than the 300,000 figure. Ollama's lack of built-in telemetry means no one, including Ollama, knows the real patch adoption rate.

The Strongest Case Against Panic

A reasonable counterargument is that Bleeding Llama requires the attacker to reach the Ollama API endpoint, and responsible operators put authentication proxies and firewalls in front of exposed services. A well-configured deployment behind Nginx with mutual TLS and network-level access controls is not vulnerable to remote exploitation. SentinelOne data showing 56% of hosts on residential ISPs suggests a substantial fraction of the exposure is hobbyist and experimental, not production-critical enterprise infrastructure carrying regulated data. Because the bug is in a specific quantization code path, not in the core inference pipeline, operators who disabled model creation via API policy are unaffected.

All of this is true. None of it changes the structural argument. But 300,000 servers are running real workloads, holding real secrets. And the next GGUF-style parser bug in the next AI framework will find the same kind of exposure.

What You Can Do

If you run Ollama, the immediate checklist is short and non-negotiable. Upgrade to v0.17.1 or later right now. If your instance was ever internet-accessible before patching, rotate every secret that was loaded as an environment variable: API keys, database credentials, cloud tokens, SSH keys. Don't assume you weren't hit. The exploit leaves no trace.

For the longer term, the pattern is the same one that eventually matured for Redis and MongoDB. Never expose Ollama without an authentication proxy (Nginx, Caddy, or a dedicated API gateway). Restrict /api/create and /api/push endpoints to trusted internal IPs. Monitor outbound traffic for unexpected model push operations to unfamiliar registries. And add Ollama to your vulnerability scanning pipeline, which means subscribing to Ollama's GitHub releases directly, because you cannot rely on CVE databases to surface security-critical patches within any reasonable timeframe.

If you're evaluating self-hosted AI frameworks for enterprise deployment, treat the model file parser as a security boundary. Ask whether the framework validates tensor dimensions against actual buffer sizes. Ask whether model creation accepts files from unauthenticated sources. Ask what happens when a model push goes to an unexpected destination. If the answers are "we trust the file" and "we don't monitor that," you are running a pre-Heartbleed TLS stack, except the plaintext you're leaking isn't session cookies. It's everything your people are telling the AI.

The Bottom Line

Bleeding Llama is Heartbleed for the AI age: same root cause, same silence, same scale, worse data. Twelve years separate the two vulnerabilities, tracing the migration of critical infrastructure from web servers to inference servers and the security lessons that didn't travel with it. Ollama patched the specific bug. But the structural vulnerability, model file formats treated as trusted input by parsers that allocate memory based on attacker-controlled metadata, will appear in the next framework, and the one after that. Those 300,000 servers exposed today are not an anomaly. They are the baseline. The number goes up from here.
